# SQLite-to-PostgreSQL One-Time Transfer Runbook

This runbook covers only creation and population of an **unexposed, disposable, unaccepted PostgreSQL target**. It does not authorize production execution, runtime cutover, sequence acceptance, or application traffic. Tasks 3.1 through 3.3 must be complete before this procedure is used. Production preparation and cutover require the separate approvals and stop gates in tasks 3.6, 3.7, and 3.10.

## Non-negotiable safety rules

- Keep Laravel in maintenance mode and stop writable HTTP processes, queue workers, schedulers, persisting Reverb/event consumers, and manual writers before taking the final source snapshot.
- Use only a restoration-tested, checksummed SQLite backup opened through SQLite URI `mode=ro` with `PRAGMA query_only = ON`.
- Keep the target unreachable by application and worker traffic. It must contain only the schema produced by checked-in migrations and no authoritative rows.
- Never run `migrate:fresh`, `migrate:refresh`, `db:wipe`, a seeder, a factory, truncation, or an Eloquent-based copy.
- Never place a password, `APP_KEY`, token, Reverb secret, production hostname, connection URL, or row payload in a command, log, manifest, or source-controlled file. Supply credentials through the approved secret mechanism.
- A failed gate or transfer means stop. Discard and recreate the unaccepted target from the canonical migrations. Do not resume or merge a partial target.
- The source SQLite file is immutable. The utility never authorizes cutover and never deletes backup artifacts.

## 1. Collect prerequisite evidence

Retain the redacted manifests from `MigrationPreflight` and `SourcePreparation`. Confirm all of these values from independently reviewed evidence:

- preflight passed;
- source preparation passed and source checksum did not change;
- SQLite backup restoration test passed;
- target identity is dedicated and target application traffic is disabled;
- target is still unaccepted;
- session mode is either approved continuity with the existing `APP_KEY` retained, or approved forced logout;
- environment and configuration-cache backups are protected outside source control.

Stop if any item is absent, failed, waived, or ambiguous.

## 2. Create the canonical target schema

Point a temporary, isolated deployment process at the dedicated target using either an unset `DB_URL` plus individual `DB_*` values, or one complete `DB_URL`; never both. Retrieve all sensitive values from the deployment secret mechanism.

Run only the checked-in migrations non-interactively:

```text
php artisan migrate --force
php artisan migrate:status
```

Do not add `--seed`. Compare migration names and target schema metadata with the repository and source inventory. Keep `cache` and `cache_locks` empty. The target `migrations` rows are generated by Laravel and are not copied from SQLite.

Stop and discard the target if a migration fails or schema parity is not proven. Do not edit a live target manually.

## 3. Execute the transfer utility

The operator-owned one-time harness must obtain its PostgreSQL PDO credentials from the secret mechanism, create the SQLite PDO from the protected backup with URI `mode=ro`, enable `PRAGMA query_only = ON`, and call:

```php
$utility = new App\Database\Migration\OneTimeMigrationUtility(batchSize: 500);

$manifest = $utility->transfer($readOnlySqlite, $unexposedPostgreSql, [
    'preflight_passed' => true,
    'source_preparation_passed' => true,
    'backup_is_restorable' => true,
    'canonical_schema_created' => true,
    'canonical_migrations_verified' => true,
    'target_is_unaccepted' => true,
    'target_application_traffic_disabled' => true,
    'source_checksum_before' => '<sha256-from-source-preparation>',
    'source_checksum_after_preparation' => '<same-sha256>',
    'backup_reference' => '<restricted-artifact-reference>',
    'backup_checksum_sha256' => '<backup-sha256>',
    'session_mode' => '<transfer-or-forced_logout>',
    'session_continuity_approved' => true, // required only for transfer
    'app_key_retained' => true,           // required only for transfer
    'forced_logout_approved' => true,      // required only for forced_logout
]);

$utility->writeManifest('<restricted-new-manifest-path>', $manifest);
```

The harness must not print connection details or caught PDO exception text. The utility requires the source PDO driver to be SQLite in query-only mode and the target PDO driver to be PostgreSQL. It verifies all transfer tables are empty before beginning.

The utility performs one target transaction, uses parameterized raw PDO statements, and loads bounded primary-key-ordered batches in this dependency-safe order:

1. users with `pharmacy_id` deferred;
2. pharmacies;
3. restore users' original `pharmacy_id` values;
4. medicines and suppliers;
5. inventory items;
6. messages;
7. cycle counts and cycle count items;
8. controlled-substance logs, returns/recalls, and inventory audits;
9. search logs, notifications, activity logs, and survey responses;
10. sessions only under approved continuity.

It never copies `migrations`, `cache`, or `cache_locks`. It preserves explicit primary keys and opaque values, validates PostgreSQL-sensitive types, compares source/target counts, key ranges, and canonical hashes before commit, and rolls back on any failure. Diagnostics include only reason, table, primary key, and column; they never include row values.

## 4. Review the transfer manifest

A successful task-3.4 transfer manifest must show:

- `transfer_passed: true` and `abort_required: false`;
- `cutover_performed: false`, `runtime_change_permitted: false`, and `target_application_traffic_permitted: false`;
- every prerequisite and transfer gate passed;
- equivalent source/target row counts, primary-key ranges, and canonical SHA-256 hashes for every selected authoritative table;
- zero invalid normalized values;
- cache operational exceptions and canonical migration handling;
- sequence state `pending_task_3_8_repair_and_verification`.

The last sequence state is intentional and blocks acceptance. Explicit imported IDs do not advance PostgreSQL sequences. Task 3.8 must repair and transactionally probe each listed identity sequence before any cutover can be considered.

If the manifest reports failure, retain it as redacted evidence, confirm the SQLite checksum remains unchanged, discard/recreate the unaccepted target, correct the cause in rehearsal, and start again from the beginning. Never continue a partially accepted target.

## 5. Stop boundary

Completion of this runbook produces only an unaccepted transferred target. Do not change `.env`, rebuild runtime configuration cache, restart application services against PostgreSQL, enable target traffic, or permit writes. Continue only through the separately approved rehearsal, production preparation, verification, sequence repair, backup-restore, and cutover tasks in the specification.
