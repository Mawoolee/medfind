# PostgreSQL Reverb Deployment Config Fix Bugfix Design

## Overview

MedFind currently contains a PostgreSQL connection definition, but a fresh environment copied from `.env.example` selects SQLite. Merely changing `DB_CONNECTION` would point the application at an empty PostgreSQL database and leave existing SQLite records behind. The immediate implementation increment therefore performs a controlled, one-time migration of the existing SQLite database to PostgreSQL while retaining identifiers, relationships, application data, and migration history.

The migration will use Laravel's checked-in migrations as the canonical PostgreSQL schema, transfer existing rows without invoking Eloquent events or seeders, normalize SQLite values that PostgreSQL types reject, reset PostgreSQL identity sequences, and switch the runtime only after verification passes. It will preserve the existing SQLite database as a read-only rollback artifact and keep PHPUnit's explicit SQLite `:memory:` configuration unchanged.

This design covers the database portion of the broader PostgreSQL/Reverb deployment bug: Requirements 1.1, 1.3, 2.1, 2.3, 2.6, 3.1, 3.3, 3.5, and 3.6. Reverb broadcaster deduplication, secure WebSocket proxying, and Nginx/TLS deployment remain follow-up implementation increments under the same spec; the database migration must not change event channels, payloads, or Reverb behavior.

No migration is executed by this design phase. No application source, runtime environment, or database is modified.

## Glossary

- **Bug_Condition (C)**: A deployment state in which MedFind is intended to use PostgreSQL but still selects SQLite, lacks a usable PostgreSQL target, or would lose/diverge from SQLite data when switched.
- **Property (P)**: A completed PostgreSQL cutover in which the target schema is current, authoritative records are equivalent to SQLite, relationships are valid, identities can generate collision-free keys, and the application selects PostgreSQL.
- **Preservation**: Existing records, primary keys, foreign-key relationships, credentials, timestamps, JSON content, application behavior, and isolated test behavior that must remain unchanged.
- **Source_Database**: The existing `database/database.sqlite` file, opened read-only for inventory and transfer after writers are stopped.
- **Target_Database**: A dedicated PostgreSQL database created for MedFind and initially treated as disposable until all verification gates pass.
- **Canonical_Schema**: The PostgreSQL schema produced by running the checked-in files in `database/migrations` in timestamp order.
- **Authoritative_Table**: A table containing application or user state that must be transferred exactly: `users`, `pharmacies`, `medicines`, `inventory_items`, `messages`, `suppliers`, `controlled_substance_logs`, `cycle_counts`, `cycle_count_items`, `returns_recalls`, `inventory_audits`, `search_logs`, `notifications`, `activity_logs`, `survey_responses`, and `sessions` when session continuity is required.
- **Operational_Table**: Framework-managed state that may be deliberately regenerated rather than treated as business data: `migrations`, `cache`, and `cache_locks`. The target `migrations` table is generated by Laravel; cache tables are cleared by design.
- **Transfer_Manifest**: A machine-readable record of source/target table names, row counts, primary-key ranges, canonical row hashes, sequence values, migration status, backup checksums, and verification outcomes.
- **Quiescence_Window**: A maintenance period in which HTTP writes, queue workers, schedulers, Reverb workers that can persist state, and manual database writes are stopped.
- **Identity_Sequence**: The PostgreSQL sequence backing an auto-incrementing `id` column; it must be advanced after explicit source IDs are imported.
- **Migration_Utility**: A one-time, auditable transfer process using read-only SQLite access and transactional PostgreSQL inserts. It bypasses Eloquent models, observers, events, broadcasts, queues, and seeders.
- **Test_Database**: PHPUnit's explicit `DB_CONNECTION=sqlite` and `DB_DATABASE=:memory:` database from `phpunit.xml`, which must never resolve to the production PostgreSQL database.

## Bug Details

### Bug Condition

The defect occurs when a MedFind installation with existing SQLite state is prepared for PostgreSQL but the environment still selects SQLite, PostgreSQL prerequisites are absent, or operators switch the connection before creating and validating an equivalent PostgreSQL schema and data set. In those states, MedFind either continues using the wrong engine, fails to connect, or appears to have lost its data because it is reading an empty or partial target.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type MigrationContext
  OUTPUT: boolean

  intendedPostgreSQL := input.intendedDatabaseEngine = "pgsql"
  sourceHasState := input.sqliteFileExists
                    AND input.sqliteIsReadable
                    AND input.sqliteAuthoritativeRecordCount >= 0
  targetNotReady := NOT input.pdoPgsqlAvailable
                    OR NOT input.postgreSQLReachable
                    OR NOT input.targetCredentialsAuthorized
                    OR NOT input.targetSchemaMatchesCanonicalMigrations
  transferNotProven := NOT input.authoritativeRowsEquivalent
                       OR NOT input.foreignKeysValid
                       OR NOT input.identitySequencesSafe
  runtimeStillWrong := input.runtimeDatabaseEngine != "pgsql"

  RETURN intendedPostgreSQL
         AND (runtimeStillWrong
              OR targetNotReady
              OR (sourceHasState AND transferNotProven))
END FUNCTION
```

A migration attempt must abort rather than partially cut over when any precondition or verification predicate is false.

### Examples

- `.env.example` is copied unchanged. Expected: the deployment explicitly selects `pgsql`; actual: `DB_CONNECTION=sqlite`, so database-backed requests use `database/database.sqlite`.
- An operator changes only `DB_CONNECTION=pgsql`. Expected: existing users, pharmacies, inventory, messages, notifications, and audit history remain available; actual: a new or empty PostgreSQL database contains none of the SQLite records.
- Rows are copied with explicit IDs but PostgreSQL sequences are not reset. Expected: the next insert receives an ID greater than the imported maximum; actual: a later insert can collide with an existing primary key.
- SQLite boolean values `0` and `1` or JSON text are inserted without normalization. Expected: valid PostgreSQL `boolean` and `json` values; actual: the import may fail or produce type-invalid content.
- `users` are imported with `pharmacy_id` before `pharmacies` exist. Expected: the circular user/pharmacy references are retained; actual: immediate PostgreSQL foreign-key checks reject the rows.
- PHPUnit runs after the production default changes. Expected: `RefreshDatabase` recreates only SQLite `:memory:`; actual risk: a missing test override could run destructive database refresh commands against PostgreSQL.
- The destructive `DemoSeeder` is used as a shortcut. Expected: source records are retained exactly; actual: core tables are truncated and replaced with demo records.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Every authoritative SQLite row must remain represented in PostgreSQL with the same primary key and semantically equivalent column values.
- User-to-pharmacy, inventory, message, verification, audit, cycle-count, recall, notification, survey, and other existing relationships must remain valid.
- Password hashes, remember tokens, encrypted-file references, roles, permissions, timestamps, nullable values, decimal values, UUIDs, and JSON payloads must not be regenerated or semantically changed.
- The migration must not run seeders, model factories, `migrate:fresh`, `migrate:refresh`, `db:wipe`, truncation, or any command that replaces existing business data.
- Existing SQLite must remain untouched and recoverable until PostgreSQL acceptance is complete; the migration utility must open it read-only.
- Existing Reverb channels, event payloads, authorization, queue behavior, and client-visible real-time behavior must remain unchanged.
- PHPUnit must continue to use the explicit isolated SQLite `:memory:` database declared in `phpunit.xml`; `RefreshDatabase` must never target deployment PostgreSQL.
- Explicit environment-specific PostgreSQL host, port, database, username, password, SSL mode, and optional URL settings must continue to override defaults.
- No literal password, application key, Reverb secret, access token, or production host credential may be copied from `.env` into checked-in examples or migration artifacts.

**Scope:**
All behavior outside the database-engine cutover is unaffected. In particular:
- Application routes, responses, authorization, search, inventory, messaging, and administrative workflows remain unchanged.
- File contents under `storage` are not moved by the database migration; their database path references are preserved and independently checked for referential file availability.
- `cache` and `cache_locks` may be intentionally empty on PostgreSQL because they are transient. This exception must be recorded in the transfer manifest.
- `migrations` is generated by running the canonical migration files against PostgreSQL rather than copied from SQLite; migration-name parity is verified.
- Session rows are transferred only while all writers are stopped and the same `APP_KEY` is retained. If session continuity is intentionally waived, forced logout must be an explicit, approved exception in the manifest.
- Reverb, Nginx, and TLS changes are outside this immediate data-migration increment.

## Hypothesized Root Cause

1. **SQLite remains the deployable default**: `.env.example` sets `DB_CONNECTION=sqlite`, and `config/database.php` falls back to SQLite when the variable is absent.
   - The repository already defines a `pgsql` connection with host, port, database, username, password, charset, and SSL mode settings.
   - Current setup guidance says PostgreSQL should be running, but copying the template selects SQLite.

2. **Configuration change is being conflated with data migration**: switching the connection selects a different database but does not copy schema or records.
   - Laravel migrations can construct the target schema, but they do not transfer data from SQLite.
   - Running seeders would create or replace synthetic records, not preserve existing data.

3. **Engine type differences require explicit conversion**: SQLite's dynamic typing accepts representations PostgreSQL rejects.
   - Boolean columns include `medicines.requiresPrescription`, `inventory_items.cold_chain`, and `messages.is_read`.
   - JSON columns include `pharmacies.requirements` and `messages.attachments`.
   - Decimal, date, timestamp, nullable, UUID, and text values require lossless, validated mapping.

4. **Schema dependencies complicate naive table-order copying**: `users.pharmacy_id` references `pharmacies.id`, while `pharmacies.user_id` references `users.id`.
   - Users must first be staged with `pharmacy_id = NULL`, pharmacies loaded afterward, and the original user references restored in a second pass.
   - Child tables must be loaded after their referenced parents.

5. **Explicit imported IDs do not advance PostgreSQL sequences**: inserting source IDs bypasses sequence allocation.
   - Every integer identity table must run a `setval` operation based on its imported maximum.
   - `notifications.id` is a UUID and requires no sequence reset.

6. **Test refresh behavior is destructive by design**: most feature tests use `RefreshDatabase`, which invokes fresh migrations.
   - `phpunit.xml` currently protects deployment data by forcing SQLite `:memory:`.
   - Removing or weakening those overrides could cause tests to target PostgreSQL and erase non-test data.

7. **Schema history contains an intentional enforcement gap**: `inventory_items.supplier_id` is added as a nullable integer before `suppliers` exists and has no database foreign-key constraint.
   - The model defines the relationship, so transfer verification should report orphan supplier IDs.
   - This migration must reproduce the canonical schema and must not introduce an unrelated constraint that could reject currently accepted data.

## Correctness Properties

Property 1: Bug Condition - Complete SQLite-to-PostgreSQL Cutover

_For any_ migration context where `isBugCondition` returns true and all documented prerequisites are satisfied, the migration process SHALL either abort without changing the active runtime connection or produce a PostgreSQL target for which `expectedBehavior` returns true before cutover.

```
FUNCTION expectedBehavior(result)
  INPUT: result of type MigrationResult
  OUTPUT: boolean

  RETURN result.runtimeDatabaseEngine = "pgsql"
         AND result.targetSchemaMatchesCanonicalMigrations
         AND result.authoritativeTableCountsMatch
         AND result.canonicalRowHashesMatch
         AND result.primaryKeysPreserved
         AND result.foreignKeyOrphanCount = 0
         AND result.uniqueConstraintViolationCount = 0
         AND result.invalidTypedValueCount = 0
         AND result.nextIdentityValuesExceedImportedMaxima
         AND result.databaseSmokeChecksPass
         AND result.backupIsRestorable
END FUNCTION
```

**Validates: Requirements 2.1, 2.3, 2.6**

Property 2: Preservation - Existing Data, Behavior, and Test Isolation

_For any_ source record or application/test input where the database migration bug condition does not require a semantic change, the PostgreSQL-backed application SHALL produce the same domain-visible result as the SQLite-backed application, preserving identifiers, values, relationships, credentials, authorization, Reverb behavior, and file references, while automated tests SHALL continue to target only SQLite `:memory:`.

**Validates: Requirements 3.1, 3.3, 3.4, 3.5, 3.6**

## Fix Implementation

### Changes Required

The implementation is a gated migration runbook and one-time transfer utility, not an in-place application feature. Every phase writes its outcome to the transfer manifest. Any failed gate stops the process before runtime cutover.

**Files and configuration surfaces**:
- `.env.example`: make PostgreSQL the single database default and list non-secret placeholders for every required PostgreSQL value.
- Deployment-only `.env`: supply real values out of source control; retain the existing `APP_KEY` so encrypted data and sessions remain usable.
- `config/database.php`: use the existing `pgsql` connection mapping; no model or controller changes are required for the migration.
- `phpunit.xml`: retain explicit `DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`, and `DB_URL=` overrides.
- `database/migrations/*.php`: remain the canonical schema source and run unchanged unless preflight proves a PostgreSQL incompatibility.
- A one-time migration runbook/utility: inventory, transfer, normalize, verify, and report without Eloquent or seeders.

### 1. Environment Configuration

The checked-in template will declare names, safe local defaults where appropriate, and replacement placeholders rather than real credentials:

```dotenv
DB_CONNECTION=pgsql
DB_HOST=<postgres-host>
DB_PORT=5432
DB_DATABASE=<postgres-database>
DB_USERNAME=<postgres-username>
DB_PASSWORD=<replace-with-secret>
DB_CHARSET=utf8
DB_SSLMODE=<require-or-provider-required-mode>
```

`DB_URL` must either be unset/empty or documented as an alternative complete connection string. Operators must not set a stale `DB_URL` that conflicts with individual `DB_*` values. Production secrets are supplied through the deployment secret mechanism and never copied from the local `.env` into documentation, logs, commands, or the manifest. After any cutover or rollback environment change, Laravel configuration cache must be cleared and rebuilt before services restart.

This increment will not alter Reverb values, but changing `.env.example` must not add another `BROADCAST_CONNECTION` declaration or expose Reverb credentials.

### 2. PostgreSQL and Driver Prerequisites

Before quiescence, preflight must verify and record:

1. A supported PostgreSQL server is reachable over the intended host, port, and TLS policy.
2. The PHP runtime used by both web and CLI exposes `PDO`, `pdo_pgsql`, and `pgsql`; `PDO::getAvailableDrivers()` includes `pgsql`.
3. SQLite read support remains available for transfer (`pdo_sqlite` and `sqlite3`).
4. `psql`, `pg_dump`, and `pg_restore` or approved equivalent backup tools are installed and version-compatible with the server.
5. The target database uses UTF-8 and the intended timezone/collation policy is recorded.
6. The migration role can connect, create schema objects, run migrations, insert/update/select/delete during transfer, and use/update sequences. The long-lived application role receives only runtime privileges after migration.
7. The target is empty, or a backup and explicit replacement approval exist. The process must never merge into an unknown populated target.
8. Free disk space is sufficient for the SQLite backup, transfer artifacts, PostgreSQL target, dumps, and logs.
9. The SQLite integrity check passes, the source file is readable, and no unexpected tables or columns remain unclassified.
10. Source unique keys and would-be PostgreSQL constraints have no violations. Failures must be resolved or explicitly mapped before import.

Repository inspection on the current workstation found `pdo_pgsql`, `pgsql`, `pdo_sqlite`, and `sqlite3`, but deployment preflight must repeat these checks in the actual web and CLI runtimes.

### 3. Backup, Quiescence, and Source Inventory

1. Announce a maintenance window and prevent new writes.
2. Stop queue workers, schedulers, writable HTTP processes, and any Reverb/event consumer that can persist records. Confirm no SQLite write transaction remains.
3. Copy `database/database.sqlite` at the filesystem level only after quiescence, store it with restrictive permissions, and record a cryptographic checksum, size, timestamp, and source path.
4. Preserve a protected copy of the deployment environment and current configuration-cache state outside source control. Never put secret values in the manifest.
5. If the PostgreSQL target pre-exists, take and test a PostgreSQL-format backup before changing it.
6. Open the migration source using a read-only SQLite URI/mode. The transfer utility must reject writable source access.
7. Inventory `sqlite_master`, table columns, indexes, foreign keys, row counts, primary-key minima/maxima, and migration names. Compare them with the checked-in migration-derived schema.
8. Classify every source table as authoritative, operational, or explicitly excluded. Abort on unknown tables rather than silently dropping their data.
9. Produce a pre-transfer manifest and retain it with backups.

### 4. PostgreSQL Schema Migration

1. Create or select a dedicated empty PostgreSQL database; do not point MedFind traffic at it yet.
2. Configure a temporary deployment process to target that database and run the normal checked-in Laravel migrations with `--force`. Never use `migrate:fresh`, `migrate:refresh`, `db:wipe`, or `--seed`.
3. Record `migrate:status` and compare the target migration names with the source and repository migration list.
4. Verify PostgreSQL table, column, nullability, default, primary-key, unique-index, and foreign-key metadata before inserting data.
5. Preserve the canonical absence of a foreign key on `inventory_items.supplier_id`; report invalid supplier references, but do not add a new constraint in this bugfix.
6. Abort if any checked-in migration is PostgreSQL-incompatible. Re-hypothesize and design a forward schema correction rather than editing a live target manually.

### 5. Safe Existing-Data Transfer

The transfer utility uses parameterized raw database operations and a PostgreSQL transaction. It must not instantiate Eloquent models, hash passwords, fire observers/events, broadcast, queue jobs, or call any seeder.

**Normalization rules:**
- Preserve integer IDs as 64-bit integers.
- Convert only accepted SQLite boolean representations (`0`, `1`, `"0"`, `"1"`, true, false) to PostgreSQL booleans; abort on any other value.
- Validate `pharmacies.requirements` and `messages.attachments` as JSON before insertion and preserve their decoded semantic value. Preserve SQL `NULL` as `NULL`, not JSON `null` or an empty object/array.
- Transfer decimal values such as price, latitude, and longitude as exact decimal strings, never through binary floating-point formatting.
- Validate dates and timestamps, preserve nullability and represented instant/value, and use one declared timezone interpretation.
- Preserve empty strings separately from `NULL`.
- Preserve UUID notification IDs and validate UUID syntax.
- Preserve password hashes, remember tokens, opaque payloads, encrypted-file paths, session payloads, and notification data byte-for-byte unless PostgreSQL encoding validation proves the source invalid.
- Reject invalid UTF-8 or out-of-range values with a table, primary key, and column diagnostic that does not disclose secrets.

**Dependency-safe load order:**
1. Load `users` with the original `pharmacy_id` captured in a side map and insert `pharmacy_id = NULL`.
2. Load `pharmacies` with `user_id` references to the already loaded users.
3. Restore each mapped `users.pharmacy_id` and verify the circular relationship.
4. Load `medicines` and `suppliers`.
5. Load `inventory_items`.
6. Load `messages`.
7. Load `cycle_counts`, then `cycle_count_items`.
8. Load `controlled_substance_logs`, `returns_recalls`, and `inventory_audits`.
9. Load `search_logs`, `notifications`, `activity_logs`, and `survey_responses`.
10. Load `sessions` if continuity was approved.
11. Do not copy `cache` or `cache_locks`; initialize them empty and record the exception.
12. Do not copy `migrations`; retain the migration records generated by the canonical PostgreSQL schema migration and verify name parity.

Within each table, deterministic primary-key order and bounded batches make failures reproducible. The target remains inaccessible to application traffic throughout transfer. A failed transfer rolls back the target transaction or discards/recreates the unaccepted target; the SQLite source remains untouched.

### 6. Identity and Sequence Handling

After explicit IDs are loaded, reset every integer identity sequence:

```sql
SELECT setval(
  pg_get_serial_sequence('<table>', 'id'),
  COALESCE((SELECT MAX(id) FROM <table>), 1),
  EXISTS (SELECT 1 FROM <table>)
);
```

With rows present, the sequence is marked called at `MAX(id)`, so the next value is greater than the imported maximum. For an empty table, it is set to `1` with `is_called = false`, so the first generated value is `1`.

Apply and verify this rule for:
- `users`
- `pharmacies`
- `medicines`
- `inventory_items`
- `messages`
- `suppliers`
- `controlled_substance_logs`
- `cycle_counts`
- `cycle_count_items`
- `returns_recalls`
- `inventory_audits`
- `search_logs`
- `activity_logs`
- `survey_responses`

`notifications.id`, `sessions.id`, `cache.key`, and `cache_locks.key` are not sequence-backed. The generated `migrations` table keeps the sequence state created by Laravel. For each application identity table, a transactional probe must request a default ID, assert it exceeds the imported maximum, and roll back the probe.

### 7. Verification and Cutover Gates

Cutover is allowed only when all checks pass and are recorded:

**Schema checks:**
- All repository migrations report as applied on PostgreSQL.
- Expected tables, columns, types, defaults, indexes, unique constraints, nullability, and foreign keys match the canonical schema.
- No unclassified source table or column is omitted.

**Data checks:**
- Source and target row counts match for every authoritative table.
- Primary-key sets, minima, and maxima match.
- Canonical per-row and per-table hashes match after documented type normalization. Hashing must use deterministic column order, primary-key order, explicit null markers, stable JSON key ordering, and exact decimal/timestamp representations.
- Boolean, JSON, date, timestamp, decimal, UUID, and UTF-8 validation reports zero invalid values.
- File-reference samples and totals confirm that referenced prescription, attachment, logo, and requirement files still exist under storage; files themselves are not copied by this database step.

**Relationship checks:**
- PostgreSQL reports no foreign-key violations.
- Explicit orphan queries return zero for every relationship, including unconstrained `inventory_items.supplier_id` when non-null.
- The circular `users.pharmacy_id` and `pharmacies.user_id` links match source values.
- Unique keys such as `users.email` and `(inventory_items.pharmacy_id, inventory_items.medicine_id)` have no duplicates.

**Identity checks:**
- Every listed sequence has a next generated value greater than the imported maximum.
- Probe inserts are rolled back and leave row counts/hashes unchanged.

**Application checks on the unexposed target:**
- Laravel reports the `pgsql` driver and expected database without logging credentials.
- A read/write transaction can connect, write a disposable probe, read it, and roll it back.
- Representative authentication, pharmacy listing/search, inventory read/update in a rolled-back transaction, messaging, notifications, and audit queries return expected records.
- Existing password hashes authenticate without reset; existing authorization boundaries remain intact.
- Reverb configuration and event definitions show no diff from the pre-migration application build.

**Test isolation check:**
- Before running tests, inspect the resolved test environment and assert `APP_ENV=testing`, `DB_CONNECTION=sqlite`, and `DB_DATABASE=:memory:`.
- Reject test execution if the resolved database is PostgreSQL or a non-memory SQLite file.
- Run the existing non-watch test command once and verify feature suites using `RefreshDatabase` pass without touching target counts/hashes.

After every gate passes, update deployment environment selection to PostgreSQL, clear/rebuild configuration cache, restart application and worker processes, and repeat smoke checks against the active endpoint. Keep maintenance mode until active checks pass.

### 8. Rollback and Backup Strategy

**Before cutover:**
- Any failure leaves runtime on SQLite.
- Roll back/discard the unaccepted PostgreSQL target and correct the transfer process.
- Never modify or delete the SQLite source or its verified backup.

**After cutover but before accepting writes:**
- Stop/restart services in maintenance mode.
- Restore the prior environment selection for SQLite, clear/rebuild configuration cache, and restart services.
- Verify the SQLite checksum/integrity and repeat core smoke checks.

**After PostgreSQL has accepted writes:**
- Do not blindly switch back to the stale SQLite file because that would lose new PostgreSQL transactions.
- Re-enter maintenance mode, preserve a PostgreSQL dump, quantify the post-cutover delta, and choose an approved reconciliation or forward-repair plan.
- A rollback to SQLite is permitted only after those new records are safely reverse-migrated and verified, or business owners explicitly accept their loss.

**Backup retention and restoration:**
- Retain the original SQLite file, quiesced SQLite backup, transfer manifest, and final PostgreSQL dump for the approved retention period.
- Encrypt backups at rest, limit permissions, and keep secrets out of filenames and manifests.
- Test restoration to isolated locations before declaring the backup usable.
- Do not delete SQLite backups as part of the successful migration command; retirement is a separate, approved operation after the observation period.

## Testing Strategy

### Validation Approach

Validation follows the bug condition methodology in four stages: surface the current defect, prove the target schema and conversion approach in an isolated rehearsal, verify the complete migration against a disposable PostgreSQL database, and preserve non-bug behavior and test isolation. Production migration is not the first execution of the process.

### Exploratory Bug Condition Checking

**Goal**: Demonstrate the current defect and confirm or refute the root-cause hypotheses before implementation. All checks are read-only or use disposable databases.

**Test Plan**: Build a sanitized SQLite fixture that exercises every schema type and relationship, copy `.env.example` into an isolated environment, inspect resolved Laravel configuration, and rehearse the migration into disposable PostgreSQL. Do not use the real source for exploratory mutation.

**Test Cases**:
1. **Fresh Template Selection**: Resolve database configuration from `.env.example` and show that the unfixed template selects SQLite.
2. **Connection-Only Switch**: Point an isolated app instance at an empty PostgreSQL target and show that existing SQLite records are absent.
3. **Type Conversion Fixture**: Include booleans, nulls, JSON arrays/objects, decimals, timestamps, UUIDs, Unicode, empty strings, and opaque payloads; show which naive inserts fail or diverge.
4. **Circular Relationship Fixture**: Create linked user/pharmacy records and show that naive parent-first insertion cannot satisfy both immediate foreign keys.
5. **Sequence Fixture**: Import explicit IDs, omit `setval`, and demonstrate a potential generated-ID collision on disposable PostgreSQL.
6. **Unknown Schema Fixture**: Add an unclassified table/column and verify preflight aborts instead of omitting it.
7. **Test Safety Fixture**: Remove the test override only in a disposable environment and prove the safety guard refuses a PostgreSQL target.

**Expected Counterexamples**:
- The checked-in environment template resolves `database.default` to `sqlite`.
- PostgreSQL schema/data are absent after a connection-only change.
- Naive boolean or JSON insertion fails or changes meaning.
- Immediate foreign keys reject circular user/pharmacy loading.
- The next identity value is not greater than imported IDs until sequences are reset.
- A test process without explicit SQLite `:memory:` is blocked before `RefreshDatabase` runs.

### Fix Checking

**Goal**: Verify every valid migration context satisfying the bug condition either completes with all expected properties or fails closed before cutover.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  sourceSnapshot := immutableSQLiteFixture(input)
  result := runMigrationAgainstDisposablePostgreSQL(sourceSnapshot)

  IF result.preconditionsSatisfied THEN
    ASSERT expectedBehavior(result)
  ELSE
    ASSERT result.cutoverPerformed = false
    ASSERT checksum(sourceSnapshot) = result.sourceChecksumAfterAttempt
  END IF
END FOR
```

A production cutover uses the same gates proven in rehearsal; no test may write to the production source or target.

### Preservation Checking

**Goal**: Verify inputs not requiring semantic change behave equivalently on the SQLite source and PostgreSQL target.

**Pseudocode:**
```
FOR ALL input WHERE NOT requiresDatabaseEngineSpecificChange(input) DO
  sqliteResult := executeReadOrRolledBackWorkflow(sqliteSource, input)
  postgresResult := executeReadOrRolledBackWorkflow(postgresTarget, input)

  ASSERT canonicalize(sqliteResult) = canonicalize(postgresResult)
  ASSERT sqliteSourceChecksumIsUnchanged()
END FOR

ASSERT resolvedTestDatabase() = "sqlite::memory:"
```

**Testing Approach**: Property-based tests generate valid table rows and domain workflows across nullability, edge IDs, Unicode, JSON, boolean, decimal, date, and relationship combinations. Comparison uses the same canonicalization rules as the transfer manifest.

**Test Plan**: Capture source counts, hashes, relationships, representative query results, resolved Reverb configuration, and test database identity before migration. Compare them after transfer, after cutover, and after the observation window.

**Test Cases**:
1. **Record Preservation**: Every authoritative table retains count, key set, and canonical row hash.
2. **Relationship Preservation**: Every source relationship resolves to the same IDs on PostgreSQL, including circular user/pharmacy links.
3. **Credential and Authorization Preservation**: Existing password hashes, roles, permissions, and protected-route outcomes remain unchanged.
4. **Storage Reference Preservation**: Existing encrypted prescription and uploaded-file path references remain unchanged and resolvable.
5. **Reverb Preservation**: Database migration causes no change to broadcaster selection, channels, payloads, or authorization code/config.
6. **Test Isolation Preservation**: Existing feature tests continue using SQLite `:memory:` and leave PostgreSQL hashes/counts unchanged.
7. **Failure Preservation**: Injected transfer failures leave the active runtime on SQLite and leave the source checksum unchanged.

### Unit Tests

- Test `isBugCondition` and preflight gating for missing drivers, unreachable targets, non-empty targets, invalid source integrity, unknown schema, and conflicting environment values.
- Test normalization for booleans, JSON, null versus empty string, exact decimals, dates/timestamps, UUIDs, UTF-8, and opaque payloads.
- Test dependency planning and the two-pass restoration of `users.pharmacy_id`.
- Test sequence-reset SQL for empty and populated identity tables.
- Test secret redaction in logs and manifests.
- Test the hard safety guard that rejects any test database other than SQLite `:memory:`.

### Property-Based Tests

- Generate valid SQLite rows for every migrated type and assert canonical value equality after PostgreSQL round-trip.
- Generate related entity graphs and assert primary keys and foreign-key edges are isomorphic after transfer.
- Generate table sizes, sparse IDs, deleted-ID gaps, and empty tables; assert post-import sequences always produce a new non-colliding ID.
- Generate invalid booleans, malformed JSON, invalid UUIDs, broken references, duplicate unique keys, and unknown columns; assert migration aborts before cutover and preserves the source checksum.
- Generate non-migration application reads and rolled-back writes; assert SQLite and PostgreSQL produce equivalent domain results.

### Integration Tests

- Rehearse the complete backup, schema migration, transfer, verification, cutover, and pre-write rollback flow using a realistic sanitized SQLite snapshot and disposable PostgreSQL database.
- Run the existing Laravel feature suite once with PHPUnit's SQLite `:memory:` overrides, then prove PostgreSQL target counts and hashes are unchanged.
- Smoke-test authentication, pharmacy search, inventory, messaging, notifications, surveys, and audit history against the migrated PostgreSQL target.
- Verify the app and worker CLI resolve the same PostgreSQL connection and TLS mode after configuration cache rebuild.
- Verify a PostgreSQL dump restores into a second isolated database and passes the same schema/data checks.
- Exercise rollback before writes and delta-protection behavior after simulated PostgreSQL writes.
